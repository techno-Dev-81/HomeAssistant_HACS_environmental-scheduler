# Spec amendment 002.3: product fixes found by the E2E suite

Status: APPROVED 2026-10-21
Amends: .sdd/specs/002-e2e-testing.md (approved 2026-10-20), after amendments 002.1 and 002.2

## What changes
1. **Section 3, Entry point inventory** adds two rows:

   | Name | Location | Extends existing? |
   |---|---|---|
   | Room config card edit panel (fix) | `custom_components/environmental_scheduler/www/environmental-scheduler-room-config-card.js` | yes |
   | Scheduler minute tick and block-resolving services use HA's local time (fix) | `custom_components/environmental_scheduler/scheduler.py`, `custom_components/environmental_scheduler/services.py` | yes |

2. **Section 4, PB4** becomes: "The config flow, options flow, services, events and cards behave as before, and the suite only drives them, except for the two fixes in R15 and R16."

3. **Section 7** "No change to the integration's own UI." becomes: "No change to the integration's own UI layout or navigation; R15 repairs the room config card's edit panel."

4. **Section 8, Requirements** adds:
   - **R15.** Opening a room in the room config card draws its edit panel, so the settings and a working Save are shown. Before the fix the card stopped while drawing the panel, because it looked up the Save and Delete buttons with `getElementById` on a `div`, so no fields were shown and nothing could be saved. Found by scenario 18; fixed in commit c0ef18b.
   - **R16.** The scheduler and the services that resolve blocks work in HA's configured local time.
     - The minute tick converts the time HA gives it (UTC) to local time before it works out the date, the day name, the pre-heat time and the active block.
     - `get_active_block`, `get_house_status` and `get_upcoming_blocks` use HA's configured time instead of the host clock.
     - Before the fix, while local time differed from UTC, every block's `pre_block_start` event (on every installation, including Node-RED mode, because the event fires before the mode check) and, where HA controls the entities, the entity change were offset by that difference (an hour late during British Summer Time). The three services depended on the host clock matching HA's time zone. Found by scenario 22; fixed in commit f0ea788.

5. **Section 12, Testing** adds:
   - **Unit:** a scheduler test where a UTC tick during British Summer Time resolves the block at local time. It fails without the tick part of R16.
   - **E2E:** scenario 18 proves what R15 needs: the edit panel draws, "Follow house schedule" is shown, and Save stores the change with the room's other settings unchanged. The other tabs and fields are not checked. Scenario 22 proves the tick part of R16.
   - **Accepted gap:** no test fails without the services part of R16. Constitution amendments 1 and 3 keep services out of the unit suite and check them in the E2E suite, but the test container's clock already matches HA's time zone, so scenarios 6, 11, 16, 17 and 19 to 22, which call these services directly or through the cards, pass with or without the change. They give regression coverage only.

## Why
The two fixes were made during spec 002 by user decision on 2026-10-21, and are recorded in the evidence of tasks 002 T4.4 and tasks 002.1 T4.6. They change product behaviour, and R16 affects every installation. Spec 002 still described the suite as only driving the product, so the record did not show the change (CLAUDE.md: nothing disappears silently). This amendment brings the spec in line with the code. Nothing is built from it, because both fixes are already committed, deployed to the test instance and tested as stated in item 5.

## Supersedes
In spec 002: PB4; the section 7 line on the integration's own UI; section 3 gains two rows; section 8 gains R15 and R16; section 12 gains the testing lines and one accepted gap. Everything else, including amendments 002.1 and 002.2, is unchanged.
